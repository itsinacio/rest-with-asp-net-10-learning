Dockerizando uma Aplicação ASP.NET 10

Dockerizar uma aplicação ASP.NET representa um dos casos de uso mais comuns em ambientes corporativos modernos. O processo envolve criar um Dockerfile que não apenas empacota a aplicação, mas também otimiza o tamanho da imagem final e garante que apenas os artefatos necessários para execução estejam presentes no ambiente de produção. Nesta aula, exploraremos o passo a passo completo para containerizar uma aplicação ASP.NET 10, utilizando a técnica de multistage build para maximizar eficiência e segurança.

1. Pré-requisitos

Antes de iniciar o processo de dockerização, certifique-se de ter instalado:

  • Docker Desktop ou Docker Engine (versão 20.10 ou superior)
  • .NET SDK 10.0-preview (para desenvolvimento local, se necessário)
  • Visual Studio 2022, Visual Studio Code ou qualquer editor de sua preferência
  • Uma aplicação ASP.NET 10 funcional (pode ser criada com dotnet new webapi)

2. Estrutura do projeto

Para este exemplo, utilizamos uma estrutura completa de projeto ASP.NET com separação de responsabilidades:

01-Before/ │ HelloDocker.sln │ Dockerfile │ └───HelloDocker/ │ appsettings.Development.json │ appsettings.json │ HelloDocker.csproj │ HelloDocker.http │ Program.cs │ ├───Controllers/ │ DockerController.cs │ ├───Model/ │ HelloDocker.cs │ ├───Properties/ │ launchSettings.json │ └───Services/ InstanceInformationService.cs

O Dockerfile deve ser posicionado na raiz da solução, um nível acima do diretório do projeto, para que o contexto de build inclua todos os arquivos necessários. Esta estrutura segue o padrão recomendado para aplicações ASP.NET, com separação clara entre controladores, modelos e serviços.

3. Criando o Dockerfile

O Dockerfile a seguir utiliza a técnica de multistage build, separando as etapas de compilação e execução em diferentes estágios. Isso garante que a imagem final contenha apenas o runtime necessário, sem ferramentas de desenvolvimento ou código-fonte:

# Stage 1: Base - Imagem runtime para execução FROM mcr.microsoft.com/dotnet/aspnet:10.0-preview AS base USER $APP_UID WORKDIR /app EXPOSE 80 # Stage 2: Build - Imagem SDK para compilação FROM mcr.microsoft.com/dotnet/sdk:10.0-preview AS build ARG BUILD_CONFIGURATION=Release WORKDIR /src COPY ["HelloDocker/HelloDocker.csproj", "HelloDocker/"] RUN dotnet restore "./HelloDocker/HelloDocker.csproj" COPY . . WORKDIR "/src/HelloDocker" RUN dotnet build "./HelloDocker.csproj" -c $BUILD_CONFIGURATION -o /app/build # Stage 3: Publish - Publicação dos artefatos FROM build AS publish ARG BUILD_CONFIGURATION=Release RUN dotnet publish "./HelloDocker.csproj" -c $BUILD_CONFIGURATION -o /app/publish /p:UseAppHost=false # Stage 4: Final - Imagem final otimizada FROM base AS final WORKDIR /app COPY --from=publish /app/publish . ENTRYPOINT ["dotnet", "HelloDocker.dll"]

4. Entendendo o Multistage Build

O multistage build é uma técnica fundamental para criar imagens Docker otimizadas. Ao invés de incluir todo o SDK e ferramentas de compilação na imagem final, separamos o processo em etapas distintas, cada uma com sua responsabilidade específica. Isso resulta em imagens significativamente menores e mais seguras.

4.1. Stage 1: Base (Imagem Runtime)

O primeiro estágio utiliza a imagem mcr.microsoft.com/dotnet/aspnet:10.0-preview, que contém apenas o runtime ASP.NET necessário para executar aplicações. Esta imagem não inclui o SDK ou ferramentas de compilação, tornando-a muito mais leve. A instrução USER $APP_UID configura o contêiner para executar com um usuário não-root, aumentando a segurança. A porta 80 é exposta através da instrução EXPOSE, indicando que a aplicação escutará requisições HTTP nesta porta.

4.2. Stage 2: Build (Compilação)

O segundo estágio utiliza a imagem mcr.microsoft.com/dotnet/sdk:10.0-preview, que contém todas as ferramentas necessárias para compilar aplicações .NET. O argumento BUILD_CONFIGURATION permite definir o perfil de build (Release ou Debug) durante a construção da imagem. Primeiro, apenas o arquivo .csproj é copiado e o comando dotnet restore é executado. Esta estratégia aproveita o cache de camadas do Docker: se as dependências não mudarem, esta camada será reutilizada em builds subsequentes, acelerando significativamente o processo. Após o restore, todo o código-fonte é copiado e o comando dotnet build compila a aplicação.

4.3. Stage 3: Publish (Publicação)

O terceiro estágio herda do estágio de build e executa o comando dotnet publish. Este comando gera os artefatos otimizados para produção, removendo símbolos de debug e aplicando otimizações de runtime. O parâmetro /p:UseAppHost=false instrui o .NET a não criar um executável nativo, já que utilizaremos o comando dotnet para iniciar a aplicação. Os artefatos publicados são colocados em /app/publish.

4.4. Stage 4: Final (Imagem de Produção)

O último estágio retorna à base image (runtime apenas) e copia os artefatos publicados do estágio anterior usando COPY --from=publish. Esta instrução permite copiar arquivos de um estágio nomeado para outro, que é a essência do multistage build. A imagem final contém apenas o runtime ASP.NET e os binários compilados da aplicação, sem código-fonte, ferramentas de build ou dependências de desenvolvimento. O ENTRYPOINT define o comando que será executado quando o contêiner iniciar: dotnet HelloDocker.dll.

5. Vantagens do Multistage Build

  • Tamanho reduzido: A imagem final pode ser até 10 vezes menor que uma imagem que inclui o SDK completo.
  • Segurança aprimorada: Sem ferramentas de compilação ou código-fonte na imagem de produção, a superfície de ataque é drasticamente reduzida.
  • Cache eficiente: Separar o restore das dependências do build do código permite que o Docker reutilize camadas quando apenas o código muda.
  • Separação de responsabilidades: Cada estágio tem um propósito claro, facilitando manutenção e debugging.

6. Análise detalhada das instruções

6.1. FROM mcr.microsoft.com/dotnet/aspnet:10.0-preview AS base

Define a base image para o runtime. O sufixo AS base nomeia este estágio para referência posterior. A Microsoft mantém imagens oficiais otimizadas no Microsoft Container Registry (mcr.microsoft.com).

6.2. USER $APP_UID

Configura o contêiner para executar com um usuário específico ao invés de root. A variável $APP_UID é definida automaticamente pela base image da Microsoft, seguindo práticas de segurança recomendadas.

6.3. WORKDIR /app

Define o diretório de trabalho dentro do contêiner. Todos os comandos subsequentes serão executados neste diretório, e será também o diretório padrão quando o contêiner iniciar.

6.4. EXPOSE 80

Documenta que a aplicação escutará na porta 80. Esta instrução é informativa e não publica a porta automaticamente — isso deve ser feito com o parâmetro -p no comando docker run.

6.5. ARG BUILD_CONFIGURATION=Release

Define um argumento de build com valor padrão. Este argumento pode ser sobrescrito durante o build usando --build-arg BUILD_CONFIGURATION=Debug.

6.6. COPY ["HelloDocker/HelloDocker.csproj", "HelloDocker/"]

Copia apenas o arquivo de projeto antes de copiar o código-fonte. Esta estratégia otimiza o cache: se as dependências (definidas no .csproj) não mudarem, o Docker reutilizará a camada do restore.

6.7. RUN dotnet restore

Restaura todas as dependências NuGet definidas no arquivo de projeto. Esta operação pode ser demorada, mas é executada apenas quando o .csproj muda.

6.8. COPY . .

Copia todo o código-fonte do contexto de build para dentro do contêiner. É executado após o restore para maximizar a eficiência do cache.

6.9. RUN dotnet build

Compila a aplicação no modo especificado por BUILD_CONFIGURATION. Os binários compilados são colocados em /app/build.

6.10. RUN dotnet publish

Gera os artefatos otimizados para produção, aplicando tree shaking, ahead-of-time compilation quando aplicável, e removendo símbolos de debug.

6.11. COPY --from=publish /app/publish .

Esta é a instrução que materializa o multistage build. Copia os artefatos do estágio "publish" para o estágio final, sem trazer as camadas intermediárias.

6.12. ENTRYPOINT ["dotnet", "HelloDocker.dll"]

Define o comando que será executado quando o contêiner iniciar. Utiliza o formato exec (array JSON) que é preferível ao formato shell, pois permite que sinais do sistema operacional sejam tratados corretamente.

Dockerizar uma aplicação ASP.NET 10 utilizando multistage build representa a melhor prática atual para criar imagens otimizadas, seguras e prontas para produção.
